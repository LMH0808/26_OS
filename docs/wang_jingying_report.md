# 统计与实验章节材料（王晶莹）

本文是论文“实验与结果分析”章节的可用素材：设置、四张结果表、发现、代价与局限。
实验方法见 [experiment_plan.md](experiment_plan.md)，指标定义见 [experiments.md](experiments.md)。

## 一、实验设置

- 引擎：`tea_break_scheduler`（`Scheduler` + `SchedulerConfig`），单进程离散时间模型；
- 观察窗口：H = 200，所有策略相同；
- 负载：普通、台面拥堵、紧急密集、故障强度四类（构造见实验方法第 2 节）；
- 种子：1–20，共 20 个独立种子，同一 (负载, 种子) 的五种策略共用一份输入；
- 规模：4 × 20 × 5 = 400 次运行，全部成功进入结果表；
- 统计：样本均值与样本标准差（n−1），空值不填零。

## 三、主要发现

1. **常态下基线稳定。** 普通负载 20 个种子全部完成，按时率 0.9917，平均时延 4.83，
   紧急错失率 0.0435；说明默认配置在轻载下没有牺牲按时性。

2. **拥堵时先完成与先按期是两回事。** 台面拥堵下 FCFS 的完成率略高
   （0.8208 对 0.8052）、时延略低（48.01 对 50.06），但按时率明显更低
   （0.2969 对 0.399），紧急错失率从 0 升到 0.2222。FCFS 按到达顺序服务，
   先做完整批任务，代价是紧急与临近截止的任务被推后。

3. **动态重排 + 抢占对紧急任务有实际收益。** 紧急密集负载中，baseline 的紧急错失率
   0.11、fcfs/no_dynamic 0.23、non_preemptive 0.13；相应抢占次数 baseline 为 0.8，
   另外两组为 0。故障强度下同样：baseline 0.0667、fcfs 0.3。
   这两组差异方向一致，可支撑“动态 + 抢占改善紧急响应”的结论。

4. **拥堵是唯一出现未完成任务的负载。** 未完成均值 9.35（baseline）与 8.6（fcfs），
   对应完成率 0.8052 与 0.8208；其余三类负载完成率均为 1。说明 H=200 的约束在
   单实例茶歇台上确实起作用，这一指标不能只报完成率而不报积压量。

5. **安全拒绝与紧急错失不是同一件事。** `no_deadlock` 在四类负载中安全拒绝均为 0，
   紧急错失率反而更低（如紧急密集 0.025 对 0.11）。但这批负载没有形成循环等待，
   `deadlock_count` 全为 0；因此不能据此说“关闭银行家更好”，只能说银行家拒绝会
   让部分任务多等一段时间。死锁机制的比较见固定死锁对照。

## 四、代价与代价口径

- 回滚损失 `rollback_work` 与重做量 `redo_work` 在 400 次运行中均为 0：业务负载未触发回滚；
- 抢占次数最高出现在台面拥堵（baseline 1.65）与紧急密集（0.8），属于可解释的开销；
- 安全保障（银行家拒绝）在普通负载 2.95 次/组、紧急密集 6.65 次/组，是按时率提高的代价之一。

## 五、局限

1. 负载规模未按真实服务时长校准，H=200 是统一的演示窗口，不是实测工时；
2. 四类负载任务数不同（18–48），只能同类负载内比较策略，不能跨负载比较均值；
3. 单机单线程、无人员数量约束（`workers=None`），结论不外推到多人协作场景；
4. 业务负载不制造循环等待，死锁结论须引用专项对照，不能由本实验推出。

## 六、可复现性

```bash
python3 experiments/handcheck.py            # 人工核算，先通过再跑批量
python3 experiments/run_experiments.py --seeds 20
python3 experiments/summarize.py
```

- 每份结果带 `source_sha256`（调度包源码）、`input_sha256`（含配置的完整输入）、
  `workload_sha256`（仅任务/资源/事件）；
- 同一种子的五种策略 `workload_sha256` 完全一致（已验证 80 组），说明对照共用负载；
- 原始输入保存在 `experiments/results/inputs/`，可用 `run_demo.py --input` 单独重放；
- 本文所有数值来自 `experiments/results/summary.csv`（400 行明细在 `metrics.csv`）。
