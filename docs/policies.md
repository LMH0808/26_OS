# 排序模块（policies.py）

维护人：李铭昊。对应项目说明 6.1（FCFS）、6.2（优先级调度）、13.2（职责边界）、13.3（验证案例）。

## 1 职责与边界

本模块只回答一个问题：**给定一批候选任务，先执行哪个**。

| 项目 | 约定 |
|---|---|
| 输入 | 引擎已筛选的候选任务（已到达、依赖满足、当前允许运行） |
| 输出 | 排序后的任务列表；可附带每个位置的理由 |
| 不负责 | 资源申请与释放（`resources.py`）、时间推进与抢占（`scheduler.py`）、死锁三项（`deadlock.py`）、指标统计（`Metrics`） |
| 副作用 | 无。不修改任务对象、不修改调用方列表；`order_tasks` 返回新列表 |
| 依赖 | 仅标准库，兼容 Python 3.10 |

## 2 接口

```python
from tea_break_scheduler.policies import order_tasks, rank_tasks, format_ranking, selection_reason

order_tasks(tasks, "priority")     # [Task, ...]            排序结果
rank_tasks(tasks, "priority")      # [(Task, "理由"), ...]  排序结果 + 逐条理由
format_ranking(tasks, "fcfs")      # "T1 -> T2 -> T3"       一行摘要
selection_reason("fcfs")           # 策略级说明，写入运行配置
```

策略名只有 `"fcfs"` 与 `"priority"`，由 `SchedulerConfig` 校验；传入其他值抛 `ValueError`（空列表也会抛）。

## 3 排序键

排序差异只允许出现在 `_key` 一处，避免两处维护导致不一致。

### 3.1 FCFS

```
key = (submitted_at, task_id)
```

到达早者先执行；同一到达时刻按任务编号，保证重复运行结果一致。
FCFS **不看**优先级与截止时间——晚到的高优先级任务不得插队，这是它在对比实验中的价值。

### 3.2 优先级

```
key = (-priority, deadline, submitted_at, task_id)
```

优先级数值越大越靠前，因此取负号做升序；并列时依次比截止时间（早者先）、到达时刻（早者先）、任务编号。
四个位置构成全序，因此相同输入下顺序唯一、可复现。固定优先级，不含老化加分。

### 3.3 数学表述（供论文使用）

对候选集 C 与比较键 k：

```
order(C) = argmin_{t ∈ C} k(t)        （按 k 字典序取全序，再展开为序列）
```

其中 priority 策略的 `k(t) = (-p_t, d_t, a_t, id_t)`，fcfs 策略的 `k(t) = (a_t, id_t)`。

## 4 优先级定级依据

优先级是任务自带的静态属性（`Task.priority`），运行中不变；调度器只读不写。

| 任务类型 | priority | 是否带截止时间 | 理由 |
|---|---|---|---|
| 紧急送水 | 3 | 有，且紧 | 面向人，超时即客人干等 |
| 普通送水 | 2 | 软截止 | 面向人，但可稍等 |
| 整理茶歇台 | 1 | 宽松 | 维护类，晚做不影响人 |
| 回收空杯 | 1（可配置） | 宽松 | 维护类，杯子积压时可上调 |

定级逻辑两条：**面向人的服务高于维护整理；有时限的紧急任务高于普通服务**。
数值方向：**越大越优先**，与 Linux `nice` 相反（nice 越大越让出 CPU），与实时优先级方向一致。

## 5 理由生成

`rank_tasks` 对每个位置说明"它为什么排在下一个候选之前"，可直接写入事件日志：

- `优先级更高（3 > 2）`
- `同优先级，截止时间更早（20 < 30）`
- `同优先级、同截止时间、同到达时间，按任务编号（C < D）`
- `到达更早（0 < 2）`
- `已排到候选末位（其后无候选）`

**理由只描述真正参与排序的字段**（`priority`、`deadline`、`submitted_at`、`task_id`）。`urgent` 是任务的业务标记，不参与排序键，因此不会出现在理由里——否则会让人误以为"紧急"本身是排序规则，论文中也容易写错。

项目说明 6.2 要求"算法不仅要返回选择结果，还应记录原因"，这是 `rank_tasks` 存在的理由；原有的 `selection_reason` 只有策略级一句话，无法回答"这次为什么是 T2 而不是 T3"。

## 6 验证案例

数据文件 `data/policies_cases.json`：`steps`（逐轮手算）与 `expected`（预先登记的预期顺序）由人工先写，脚本只读不写。

| 案例 | 类别 | 策略 | 预期顺序 | 验证点 |
|---|---|---|---|---|
| C1 | 到达先后 | fcfs | T1 → T2 → T3 | T2 优先级最高仍排在 T1 之后 |
| C2 | 不同优先级 | priority | T2 → T1 → T3 | 与 C1 同一批任务，差异只能来自策略 |
| C3 | 同优先级并列 | priority | C → D → A → B | B 到达最早却排最后，到达时间只是第三顺位 |
| C4 | 边界：三项全并列 | priority | t1 → t2 → t3 | 前三级规则失效，只剩任务编号 |
| C5 | 边界：空候选集 | priority | （空） | 返回空列表而不抛异常，引擎可跳过本步 |

## 7 已知限制

1. 固定优先级，无老化：低优先级维护任务可能长期等待（饥饿），可用等待时长统计暴露。
2. 只看单步决策，不做全局最优，不保证完成率最优。
3. 不判断能否抢占：候选集由引擎给出，抢占由 `scheduler.py` 负责。
4. 不校验资源可用性：拿到的是已筛选候选，排序结果依赖引擎筛选口径。
5. 任务编号混合类型（int 与 str）时，`sorted` 会抛 `TypeError`；项目内编号统一为字符串。

## 8 扩展方向（论文可写）

- 老化加分：等待超过阈值后临时提升有效优先级，缓解饥饿。
- EDF 对比：`key = (deadline, submitted_at, task_id)`，作为第三组对比。
- 优先级继承：紧急任务等待低优先级持有的茶歇台时，临时提升持台任务优先级，缓解优先级反转。
